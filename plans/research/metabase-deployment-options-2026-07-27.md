# Ресёрч: футпринт Metabase и варианты развёртывания (кластер-2)

> Снимок на **2026-07-27**, read-only. Раскатка — отдельно, только с разрешения владельца.
> Тип app-БД и проброс её порта выясняет **кластер-1** (живой опрос api) — здесь не дублируется.

## Саммари (~200 слов)

Metabase — JVM-приложение (текущая ветка **Metabase 63 / OSS v0.63.x**, июль 2026). Базовый
футпринт по докам: **1 CPU + 1 ГБ RAM**, плюс **+1 CPU / +2 ГБ RAM на каждые 20 одновременных
пользователей**. **Замер локально** (`metabase/metabase:latest`, образ **1.03 ГБ**): idle RSS
**~1.46 ГиБ** без кап-heap, **~1.16 ГиБ** с `-Xmx1g`; CPU idle ~0. Под дашбордами память растёт к
`-Xmx` — на прод его надо явно капнуть.

**Метаданные:** встроенная **H2 в проде НЕЛЬЗЯ** (доки: со временем «безвозвратно повреждается»,
локи, потеря конфигов). Обязательна **внешняя app-БД — PostgreSQL** (отдельная БД/схема, не
warehouse). Сами метаданные Metabase малы (обычно десятки–сотни МБ — вопросы/дашборды/юзеры, БЕЗ
данных приложения).

**A (рядом на api):** Metabase в docker-сети приложения, app-БД по имени сервиса, порт наружу НЕ
публикуется. Дёшево, безопасно по сети; минус — конкуренция за RAM/CPU с продом (митигируется
`-Xmx` + Docker `mem_limit`/`cpus`). Бюджет: **~2 ГБ RAM (heap 1–1.5 ГБ), 1–2 vCPU, ~1.5 ГБ disk**
из 14 свободных — влезает.

**B (отдельная VM):** изоляция, но app-БД надо достучать кросс-хост (проброс порта/туннель — риск и
работа), + стоимость VM (мин. **2 vCPU / 4 ГБ / 20+ ГБ disk**).

**Рекомендация: вариант A** + внешний Postgres + read-only юзер к app-БД + UI за nginx/VPN.

## 1. Футпринт Metabase (текущая версия, 2026)

**Версия.** Актуальная релизная ветка — **Metabase 63** (июль 2026), OSS-нумерация `v0.63.x`
(последняя точечная на момент снимка — `v0.62.1.3` от 10.06.2026 в ветке 62; 63 — новейшая мажорная).
LTS поддерживается 14 мес., не-LTS — обычно ~2 мес. Продукт — один толстый JVM-jar (uberjar) в
Docker-образе на JRE (Eclipse Temurin).

**Официальные требования (доки Metabase, «Metabase in production»):**
- База: **1 ядро + 1 ГБ RAM**.
- Масштабирование Metabase: **+1 CPU и +2 ГБ RAM на каждые 20 одновременных** пользователей.
  Пример из доки: 40 одновременных → 3 ядра + 5 ГБ.
- Отдельно app-БД Postgres: база **1 CPU + 2 ГБ**, далее **+1 CPU / +1 ГБ на каждые 40 одновременных**.
- JVM heap: `JAVA_TOOL_OPTIONS: -Xmx<80% RAM>m` (оставить ~20% под non-heap).
- Порог мониторинга: CPU 80–90 %, RAM 80 %, диск app-БД 80 %.
- Пул соединений к app-БД по умолчанию 15 (`MB_APPLICATION_DB_MAX_CONNECTION_POOL_SIZE`).

**JVM heap.** По умолчанию JVM берёт max heap = 25 % от RAM хоста → на api (16 ГБ) это **до ~4 ГБ**,
даже если реально Metabase столько не нужно. На проде это надо ограничивать явно:
`JAVA_OPTS="-Xmx1g"` (или `-Xmx2g`) / `JAVA_TOOL_OPTIONS`. Полный RSS контейнера = heap + non-heap
(metaspace, потоки, off-heap) → всегда заметно больше самого `-Xmx`.

**Локальный замер (подтверждено, docker на локальном хосте, НЕ api; контейнеры удалены, образ
удалён):**

| Сценарий | Idle RSS контейнера | CPU idle | Прим. |
|---|---|---|---|
| default heap (без `-Xmx`, H2) | **~1.46 ГиБ** | ~0 (транзиент 6–8 %) | heap-cap = 25 % RAM хоста |
| `-Xmx1g` (H2) | **~1.16 ГиБ** | ~0 | non-heap ~0.16 ГиБ поверх heap |
| образ `metabase/metabase:latest` | — | — | **1.03 ГБ** на диск |
| время инициализации | — | — | ~50 c до «Initialization COMPLETE» |

Вывод по замеру: **idle floor ~1.1–1.5 ГиБ RSS** даже с капом; планировать надо не по `-Xmx`, а по
полному RSS. Под нагрузкой (несколько дашбордов/тяжёлые запросы/кэш результатов) память растёт к
`-Xmx`, CPU — всплесками на время рендера запроса.

**Диск.**
- Образ: **~1.03 ГБ**.
- app-БД (метаданные Metabase): вопросы, дашборды, коллекции, пользователи, права, история ревизий,
  лог задач, опционально кэш результатов и audit. **Данные приложения тут НЕ хранятся** — только
  метаданные. Типично **десятки–сотни МБ**, медленный рост; кэш результатов можно ограничить/выключить.
- Итого для варианта A: **~1.5–2 ГБ** диска (образ + том Postgres app-БД).

## 2. Метаданные: H2 vs внешняя (Postgres)

- **H2 (встроенная, дефолт)** — только для демо/локалки. Доки прямо: в проде **не использовать**,
  «в итоге безвозвратно повреждается» → потеря всех вопросов/дашбордов; блокировки файла, плохо
  переживает рестарты/бэкапы. **Для прод-аналитики — нет.**
- **Внешняя PostgreSQL** — официально рекомендованная (MySQL/MariaDB допустимы, но Postgres
  «настоятельно» предпочтителен). Даёт надёжность, нормальные бэкапы, безопасный рестарт/апгрейд.

**Рекомендация по метаданным:** **отдельная Postgres app-БД** (`metabase`) с собственным юзером —
либо новая маленькая БД на уже существующем Postgres api (если это Postgres — уточняет кластер-1),
либо отдельный лёгкий контейнер Postgres. Это **app-БД Metabase**, её нельзя путать с
warehouse/БД приложения, к которой Metabase подключается ЧИТАТЬ данные. Влияние на ресурсы малое:
+~0.2–0.5 ГБ RAM на процесс Postgres, диск — десятки МБ. Настраивается env-переменными
`MB_DB_TYPE=postgres`, `MB_DB_HOST/PORT/DBNAME/USER/PASS` (миграция H2→Postgres поддерживается, но
лучше сразу ставить на Postgres — чистый старт без «limited support» миграции).

## 3. Вариант A — рядом с приложением на api

Контейнер Metabase в той же docker-сети, что и приложение. app-БД (метаданные) — по имени сервиса
внутри сети; **порт 3000 наружу не публикуется** — только через nginx-vhost. К БД приложения
Metabase ходит внутренним адресом под **read-only** юзером.

- **Плюсы:** просто; БД приложения достижима внутренне (проброс наружу не нужен → кластер-1 может
  подтвердить, что порт БД и не надо открывать); нет кросс-хост экспозиции; один хост для бэкапа/логов
  (Dozzle уже есть).
- **Минусы / риски:** конкуренция за RAM/CPU с продом (orchestrator + nginx + БД приложения);
  общая судьба с хостом (падает api — падает и аналитика); тяжёлый ad-hoc запрос из Metabase может
  нагрузить БД приложения (митигация: read-only юзер + `statement_timeout`, отдельная реплика если
  появится).
- **Митигации обязательны:** `JAVA_OPTS=-Xmx1g` (или 2g), Docker `mem_limit: 2g` + `cpus: "1.5"`,
  `restart: unless-stopped`, healthcheck, nginx + basic-auth/OIDC или доступ только через VPN.

**Оценка ресурсов A (для небольшой команды, единицы одновременных пользователей):**

| Ресурс | Бюджет | Из доступного на api |
|---|---|---|
| RAM | ~2 ГБ (heap 1–1.5 ГБ + non-heap) | из ~14 ГБ свободных — ок |
| CPU | 1–2 vCPU (всплески на запрос) | из 6 vCPU — ок |
| Disk | ~1.5–2 ГБ (образ + app-БД) | ок |
| app-БД Postgres | +0.2–0.5 ГБ RAM, десятки МБ | ок |

## 4. Вариант B — отдельная машина

Metabase (+ его app-БД) на выделенной VM, изолирован от прода.

- **Плюсы:** полная изоляция ресурсов и судьбы; апгрейд/рестарт Metabase не трогает прод.
- **Минусы:** к **БД приложения надо достучаться кросс-хост** — либо публиковать порт БД наружу
  (расширяет поверхность атаки, нежелательно), либо строить туннель (WG/SSH — работа + ещё один
  отказ-путь); read-only юзер к app-БД тем более обязателен; **+стоимость VM** и её обслуживание
  (обновления ОС, бэкапы, мониторинг — ещё один хост в парке).

**Оценка ресурсов B (минимальная VM под Metabase + app-БД Postgres):**

| Ресурс | Минимум | Комфорт |
|---|---|---|
| RAM | 4 ГБ (Metabase ~2 + Postgres ~1 + ОС ~1) | 8 ГБ |
| CPU | 2 vCPU | 2–4 vCPU |
| Disk | 20 ГБ | 40 ГБ |
| Стоимость | +1 VDS (условно самый дешёвый 2/4/40 тариф) | — |

## 5. Безопасность (оба варианта)

- **Read-only к БД приложения.** Metabase подключается к warehouse под **выделенным read-only**
  юзером (`CONNECT` + `SELECT` на нужные схемы/таблицы), **не** под app-юзером приложения. Доки
  Metabase рекомендуют ровно это; write-роли (uploads/actions/transforms/persistence) — только если
  осознанно нужны фичи, по умолчанию НЕ давать. Плюс `statement_timeout` на этого юзера, чтобы
  тяжёлый ad-hoc не ронял БД.
- **UI не голым в интернет.** Только за nginx-vhost с auth (basic/OIDC) или доступ через VPN;
  порт 3000 контейнера наружу не публиковать. HTTPS обязателен.
- **Секреты** (`MB_DB_PASS`, пароль read-only юзера) — через окружение/секрет-механизм, не в argv
  (в этом репо правило то же — секрет не в командной строке).

## 6. Переиспользование существующего Metabase (контекст)

В сессии есть MCP `metabase-litellm` — это **отдельный инстанс Metabase, подключённый к БД
litellm**, не к БД приложения. Как готовый инстанс под аналитику приложения он **не подходит**
(другой источник данных, другая роль). Отмечено как контекст; если кластер-1 найдёт на api ещё
какой-то Metabase — это надо рассматривать отдельно, но текущий известный — про litellm.

## Рекомендация

**Вариант A** (Metabase рядом с приложением на api, в docker-сети приложения) с **внешней Postgres
app-БД**, read-only юзером к БД приложения, UI за nginx+auth/VPN и жёсткими лимитами
(`-Xmx` + Docker mem/cpu limits). Бюджет ~2 ГБ RAM / 1–2 vCPU / ~2 ГБ диска укладывается в ~14 ГБ
свободных на api и не требует кросс-хост экспозиции БД. Вариант B держать в резерве на случай, если
нагрузка Metabase начнёт мешать проду или потребуется жёсткая изоляция — тогда выносить на отдельную
VM с репликой БД.
